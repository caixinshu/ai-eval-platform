# Day 1：AI 应用测试与传统测试的差异

> 项目三第 1 周 · 从「断言测试」到「量化评测」

## 一、AI 测试差异对照表（7 个维度）

| 对比维度 | 传统应用 | AI 应用 |
|---------|---------|---------|
| **输出特性** | 确定性，同样输入永远同样输出 | 概率性，同样输入可能不同输出 |
| **断言方式** | 等值断言 `assert x == y` | 语义断言 / 相似度 / LLM 打分 |
| **缺陷判定** | 有明确对错，非黑即白 | 「对」是程度问题，需要阈值 |
| **测试用例** | 有限可枚举 | 输入空间近乎无限 |
| **回归测试** | 结果稳定可比 | 需多次采样取均值，结果有波动 |
| **评测指标** | 通过率 / 覆盖率 / 响应时间 | 准确率 / 忠实度 / 幻觉率 / 成本 |
| **人的作用** | 人工只写用例 | 人在回路，需要人工标注黄金答案 |

**核心转变**：传统测试的核心是「断言」，AI 评测的核心是「统计」。

---

## 二、AI 输出的非确定性来源（5 个来源 + 控制手段）

| # | 来源 | 说明 | 控制手段 |
|---|------|------|---------|
| 1 | **模型采样参数** | temperature、top_p、top_k 不同，输出就不同 | 评测时固定 temperature=0、top_p=1、seed 固定 |
| 2 | **模型版本** | 供应商静默升级模型，行为可能突变 | 报告中记录模型名称和版本，升级时重跑基线 |
| 3 | **上下文变化** | RAG 检索到的文档不同，答案就不同 | 知识库版本化，评测时记录知识库 hash |
| 4 | **Prompt 微调** | 一个词的改动可能导致输出风格大变 | Prompt 版本化管理，变更必须可回滚 |
| 5 | **长尾输入** | 用户提问方式千奇百怪，训练集外的输入表现不可知 | 构建边界集 + 对抗集，持续补充新题集 |

**关键结论**：固定 temperature=0 只能消除第 1 项，剩下 4 项必须靠「评测集 + 多次采样 + 指标量化」来覆盖。

## 三、AI 应用典型质量事故（6 类 + 根因）

| 事故类型 | 典型现象 | 根因 | 检测指标 |
|---------|---------|------|---------|
| **幻觉** | 编造不存在的事实、法规、数字 | 模型缺乏知识约束，被诱导生成 | 忠实度 Faithfulness |
| **答非所问** | 回答流畅但没解决用户问题 | 意图理解错误 / 检索偏差 | 答案相关性 Relevance |
| **上下文不忠实** | 答案与检索到的文档矛盾 | 模型忽略上下文，依赖自身先验 | 忠实度 + 上下文精度 |
| **越狱** | 被诱导输出违规内容 | 安全护栏不足 | 安全性 Safety |
| **格式错误** | 本该返回 JSON 却返回自然语言 | Prompt 约束不强 / 解析未兜底 | 格式检查（规则断言） |
| **性能劣化** | 首字延迟 3 秒以上、Token 成本翻倍 | 上下文过长 / 模型选型不当 | 响应性能 P95 / 单次成本 |

## 四、四层评测模型（L1-L4）

| 层级 | 评什么 | 怎么评 | 本周覆盖 |
|------|--------|--------|---------|
| **L1 单元层** | Prompt 模板、输出解析、格式校验 | 规则断言 / JSON Schema | Day 4（Prompt 工程） |
| **L2 组件层** | 检索质量、单轮问答准确率 | 相似度 / 规则 / LLM 打分 | Day 6-7（Ragas 评测） |
| **L3 系统层** | 端到端问答、多轮对话 | Ragas 指标 / 人工抽检 | Week 2 |
| **L4 业务层** | 用户满意度、任务完成率 | 线上反馈 / AB 实验 | Week 4 |

### 分层设计的意义

- **L1 单元层**：能自动化、能进 CI，是基础质量保障
- **L2 组件层**：核心指标层，faithfulness/correctness 等在这里算
- **L3 系统层**：真实用户体验，端到端验证
- **L4 业务层**：最终价值判断，需要线上数据

本周重点在 L1（Prompt 模板化）和 L2（Ragas 指标评测），为后续系统层和业务层打基础。
