四、四组关键实验

实验结论

top_k 实验暴露了一个更重要的口径问题：CP/CR 阈值 0.75 相对本知识库过严。

五、本周最重要的三个发现

1. 阈值必须分开管，不能共用一个

答案相似度阈值 0.84 与「片段-片段」相关性阈值 0.75 分布完全不同。实测期望片段与检索片段的最大相似度均值只有 0.7223，用 0.75 判相关性会把大量正确召回判成失败：Recall 0.382 → 阈值降到 0.65 后是 0.855。

2. 评测分数低，先分清是「系统差」还是「评测口径严」

黄金集 13.08 分看起来像系统崩了，拆开看：忠实度 1.00、安全 1.00、格式 1.00，只有「答案相关性 0.042」和「上下文精度 0.048」塌陷 —— 前者是 mock 拼接导致，后者是阈值口径导致。分段评测 + 归因矩阵让这个判断从「猜」变成「可查」。

3. 语义相似度有硬边界，细节判断必须交给 Judge

否定句 0.9843、数字互换 0.9555、型号混淆 0.9801 —— 都高于 0.84 阈值。相似度适合做粗筛，数字/否定/实体这类细节必须靠 Judge 或结构化校验兜底。

六、风险与遗留

  • 阻塞无 LLM API Key：Judge、RAG 生成段、忠实度均走降级规则，分数仅供参考
  • 未达门禁Judge 一致率 75%，低于 80% 使用门槛
  • 规模知识库仅 13 片段，检索结论（top_k=2）在扩容后需重验
  • 缺失报告无版本 diff 面板，需两次可比运行才能验证
  • 性能本机 CPU 批量编码慢，55 条 RAG 评测耗时以十分钟计

七、下周建议

  • P0 接入真实 LLM 后重跑三类基线，替换全部降级结果
  • P1 CP/CR 阈值改为配置项并校准到 0.65-0.70，写进评测配置
  • P2 扩充知识库到 50+ 片段并补同义问法，重验 top_k 曲线
  • P3 Judge 加「逐项核对数字与否定词」强制步骤，冲击 ≥90% 一致率
  • P4 报告接入 compare_runs，输出「vs 上一版」箭头与差值
